# Feature: SQLite and Migration Foundation

- **EPIC:** EPIC-01
- **Feature ID:** 03
- **Status:** Not Started
- **Source spec:** context/features/phase1-spec.md

## Goal

Create the initial SQLite schema and data-access boundary for providers and local demo sessions, with repeatable migrations and isolated test databases.

## Why This Matters

Later workflows need durable provider-scoped records. A migration-based schema prevents each feature from inventing tables or running manual SQL.

## Prerequisites

- Feature 01 backend setup is available.
- Feature 02 can start the application and perform a readiness check.
- SQLite is available locally.

## Implementation Steps

### Step 1: Configure the database engine

- **What to do:** Create a reusable SQLAlchemy engine and session factory.
- **Where:** `backend/app/db/`.
- **How:** Read the SQLite URL from settings, enable SQLite foreign keys, and expose a dependency that provides and closes a database session per request.
- **Done when:** A small database connectivity check can open and close a session without manual SQL setup.

### Step 2: Define provider and demo-session models

- **What to do:** Add the initial relational models.
- **Where:** `backend/app/models/provider.py` and `backend/app/models/demo_session.py`, or the selected model module layout.
- **How:** Add `providers` with `id`, `name`, `business_name`, `timezone`, `created_at`, and `updated_at`. Add `demo_sessions` with an opaque/hash identifier, provider ID, expiry, created-at, and revoked-at.
- **Done when:** Models have a foreign-key relationship and timestamps are stored consistently in UTC.

### Step 3: Add indexes and constraints

- **What to do:** Make provider/session lookup safe and predictable.
- **Where:** Model definitions and migration files.
- **How:** Add a foreign key from sessions to providers, an index for session lookup, an index for provider lookup, non-null constraints for required values, and an expiry/revocation representation.
- **Done when:** Invalid references are rejected and the expected lookup columns are indexed.

### Step 4: Create the first migration

- **What to do:** Add a versioned migration that creates the initial schema.
- **Where:** `backend/alembic/` or the repository's selected migration directory.
- **How:** Generate or write one migration for providers and demo sessions. Do not rely on automatic table creation in application code as the only schema setup.
- **Done when:** A new empty SQLite file reaches the latest schema through the migration command.

### Step 5: Run migrations during local startup

- **What to do:** Make first startup create the database schema automatically or through a documented startup command.
- **Where:** Backend startup/development command and migration configuration.
- **How:** Ensure migrations run before readiness succeeds. Keep production migration execution separately controllable.
- **Done when:** Deleting the local database and restarting the documented development flow recreates the schema without manual SQL.

### Step 6: Add isolated test fixtures

- **What to do:** Prevent tests from changing developer data.
- **Where:** `backend/tests/conftest.py` or the chosen test setup.
- **How:** Use a temporary SQLite database per test session or test run, apply migrations to it, and clean it up afterward.
- **Done when:** Tests pass with an empty temporary database and the developer database remains unchanged.

## Interface and Data Contracts

- Provider IDs are generated by the backend and are not accepted as authorization proof from the browser.
- Sessions store only an opaque or hashed identifier, never plaintext credentials.
- All timestamps use UTC and include created-at values.
- Raw session content and uploaded files are not stored by this feature.

## Verification

1. Run the migration command against a new temporary SQLite file.
2. Inspect the schema and confirm `providers` and `demo_sessions` exist with the expected relationship.
3. Run the readiness check and confirm it succeeds only when the database is reachable.
4. Run the database tests twice and confirm they do not modify the developer database.

## Acceptance Criteria

- [ ] SQLite connectivity is available through a repository boundary.
- [ ] Initial models and migration are present.
- [ ] Foreign keys, indexes, and UTC timestamps are configured.
- [ ] First local startup applies the schema without manual SQL.
- [ ] Tests use an isolated database.
- [ ] No credentials or raw session content are written to logs.

## Out of Scope

- Client, session-input, summary, task, appointment, or audit tables beyond the initial provider/session foundation.
- File storage for transcripts or uploads.
- PostgreSQL production migration.

## Notes

Use Alembic with SQLAlchemy unless the repository has already standardized on an equivalent migration tool. Keep model and repository APIs replaceable so SQLite can later move to PostgreSQL.
